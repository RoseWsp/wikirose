# 代码已经不是瓶颈：AI 原生开发的五关实操指南

> 同一套流程，执行者从人变成了 Agent。从想法到上线，一个人和一家公司都适用。

很多人对 AI 开发的理解，还停留在"让 AI 帮我写代码"。

这个理解没有错，但只对了一半。写代码是整个流程里变化最小、最不需要操心的一环——大模型在编码上已经训练得足够好，一句自然语言就够了。

真正改变游戏规则的，是代码两侧的事：需求怎么分析、方案怎么设计、原型怎么做、测试怎么验证。这些才是 AI 原生开发的新战场。



## 核心认知：流程没变，角色变了

AI 原生开发没有发明新流程，只是换了个方式跑旧流程。可行性分析 → 设计文档 → 原型设计 → 编码实现 → 测试验证，一步都没少。

变的是执行主体。以前每个环节都是人亲手干，现在人变成了指挥官，Agent 变成了执行者。你只在关键路径上做确认和决策，具体的分析、设计、编码、调试，全部交给 Agent 去执行。

一句话：**你从一线程序员升级成了技术总监**。不再写每一行代码，但要决定做不做、怎么做、做得对不对。

为什么流程没变，效率却能翻一个数量级？因为瓶颈转移了。以前写代码要几周几个月，所以所有确认环节都是为了在开发之前对齐；现在 Agent 几小时就能写完，**代码不再是瓶颈，瓶颈在代码两侧**——左边是设计和确认，右边是测试、验证和部署。这些环节还在以人类速度运行。

所以下面的五关，重点全在"代码之外"。

## 第一关：可行性分析——先决定要不要做

这是最容易被跳过、也最不该被跳过的一关。

**先决定要不要做，再去做。** 产品层面问：这个功能有没有价值？和产品定位匹不匹配？技术层面问：技术上能不能做到？成本是不是可控？

操作上很简单：把原始需求扔给 Agent，让它结合项目现状做一份可行性分析、列出几个技术方案。然后你快速扫一遍，基于自己的产品判断拍板。**Agent 分析和罗列方案，人做最终判断**——这就是"人在关键路径上确认"的含义，你不需要研究每个技术方案的细节，但方向和取舍得你定。

这里有个残酷的真相要提前说清楚：可行性分析是个**期望值赌注**。它大多数时候帮你避开弯路，但偶尔也会看走眼——有开发者复盘时承认，自己做过一个功能，可行性分析时觉得没问题，做完了实际体验很差，最后砍掉，浪费了几天时间和一堆 token。但这不代表这一关没用——没有它，踩的坑只会更多。

更深的机制是：**跳过关卡省下的时间，后期会以十倍还回来**。凭感觉让 Agent 直接写（vibe coding），第一周很爽，第二周开始打地鼠——改一行崩三处，越改越乱，最后被迫逐文件排查，一天的对齐比前两周加起来都累。先难后易，还是先易后难，这个选择在第一关就定下了。

## 第二关：设计文档——Agent 之间的桥梁

确认可行之后，先别急着写代码。下一步是让 Agent 写设计文档。

为什么需要文档？因为在 AI 原生开发里，文档有了全新的角色：**人和 Agent 之间、以及 Agent 和 Agent 之间的桥梁**。两个原因：

第一，文档是给你确认和修改的载体。Agent 把方案写成文档，你通读一遍，看方向对不对、细节有没有问题，直接在文档上改。

第二，文档是 Session 之间传递上下文的媒介。每一个 Agent Session 的上下文窗口是有限的，当你从"设计"进入"开发"，往往是一个全新的 Session。前一个 Session 的思考过程、决策依据、技术方案，都要通过文档传递给下一个 Session。**没有文档，下一个 Session 就是从零开始**。文档是 AI 原生开发里的"记忆载体"。

这里藏着一个更底层的原因：**Agent 的输出质量，很大程度取决于你喂给它的上下文质量**。有个被反复验证的经验是，Claude 犯的错，九成是因为上下文没给够，跟模型能力没关系。文档就是给 Agent 喂上下文的机制——喂饱了，它才不容易跑偏。

这里有个关键的操作细节：**确认后的文档，就是下一个 Agent Session 的全部起点**。当你从设计进入开发，不需要重新向 Agent 解释来龙去脉，只需要一句话："按 docs/xxx.md 实现。" 文档里已经写好了所有决策和细节，新的 Session 读完就能开始执行。

企业组织在这里多一层：文档不只是桥梁，还是审计线索。intent.md → spec.md → plan.md 的制品链全部提交进 git，谁提的需求、Agent 产出了什么、谁批准的，commit 历史全记录在案。需要合规追溯的时候，这就是全部证据。

## 第三关：高精度原型——需求、原型、UI 三合一

这是 AI 原生开发里变化最大的环节之一。

传统流程中，需求文档、原型设计、UI 设计是三个独立步骤，由不同的人完成：产品经理写需求，交互设计师做原型，UI 设计师做视觉稿。每一次交接都有信息损耗，每一次修改都要多方协调。

现在这一步可以合并成一个：**高精度原型**。一个 Agent 加上一个好的设计 skill（首推 Claude Design），就能直接产出接近最终成品的高保真设计，交互逻辑和视觉设计一次到位。这在以前是不可能的——你不可能要求一个人同时具备产品思维、交互设计和 UI 设计的能力，就算有，做一个高保真原型也要好几天。

为什么这关值得反复打磨？因为**原型阶段的修改成本极低，做出来再改的成本却指数级上升**。在原型上，改一个布局就是一句话的事；一旦开发完成，你要改代码逻辑、样式、状态管理、测试用例，成本完全不同。

还有一层更隐蔽的原因：**打磨原型，是在给你的判断力留摩擦**。AI 让搭建变得太容易了，如果省掉这层摩擦，产品会过度生长，你的品味会悄悄退化。原型阶段每一轮"这里不对，改"，都是在训练你做产品判断的肌肉。

真实案例里，原型往往要来回改很多轮：列表改成 Tab、给服务状态加图标、把功能从设置页挪到主界面……每一次调整都只需要用自然语言描述想要的变化，你的注意力全部放在"交互好不好用、界面好不好看"这些产品判断上，而不是纠结像素和布局的实现细节。

## 第四关：实现——代码已经不是瓶颈

如果你走到这一步，手里已经有了设计文档和确认过的高精度原型，那么让 Agent 写代码，对现在的模型来说，就是一件非常简单的事情。

关键技巧：**让 Agent 自行验证**。它写完一段代码会自动跑测试，发现失败会自己调试修复；改完界面会自己截图确认效果。相当于给 Agent 一个自己的反馈循环，让它在你看到结果之前先自己检查一遍。这样你作为人做最终确认时，拿到的已经是 Agent 自己验证过的结果，而不是一个粗糙的初稿。

这个阶段，人要做的事情非常少，主要就是等，偶尔看一眼进度。配合 `/goal` 这类命令，让 Agent 按文档里规划的里程碑一个个自动推进，它会自己规划实现顺序、自己写代码、自己运行测试、自己截图验证。

回头看你会意识到：**代码已经不是瓶颈了**。传统流程里那些 PRD、估时、安全审查，都是为了在开发阶段之前做好对齐——因为开发可能需要几周甚至几个月。但当 Agent 可以在几个小时内完成编码，以前的这些确认流程就需要重新审视了。

## 第五关：测试——把自己当普通用户

Agent 会帮你写测试、跑测试、验证结果，但这不代表你可以完全信赖它。接下来你需要自己动手试一试。

关键心态转变：**把自己当普通用户，而不是开发者**。

开发者测试和用户测试的视角完全不同。开发者会下意识地避开边界情况，沿着自己预期的路径操作。普通用户不会——他们会乱点、会输入你没想到的内容、会用你没预想的方式使用功能。

打开 App，假装自己第一次看到这个功能，凭直觉去用。看看提示够不够清楚，交互够不够自然，出错了有没有合理的引导。发现的问题直接扔给 Agent 修，几轮下来，功能就差不多可用了。

要不要 Code Review？这里有个更漂亮的思路：**信任流程，而不是信任制品**。没有人审查编译器输出的汇编代码——不是盲目信任编译器（编译器出过著名的灾难性 bug），而是因为构建了一整套让审查显得多余的装置：类型系统约束输出、测试套件验证行为、灰度发布加回滚兜底。对 Agent 也应该这样：与其纠结"信不信任模型"，不如问"我的验证装置建起来没有"——Agent 自验证的反馈循环、你的黑盒用户测试、随时可回滚的部署路径，就是你的装置。装置建起来了，Review 就退居二线；还没建起来，Review 就是仅剩的护栏。

## 一个人 vs 一家公司：五关相同，执行方式分叉

这是最值得琢磨的部分。同一套五关，独立开发者和企业组织走出来的形态完全不同：

| 环节 | 独立开发者 | 企业组织 |
| --- | --- | --- |
| 确认环节 | 可以合并，甚至可以跳过 Review | 每道闸门必须留痕，职责分离 |
| 治理 | 信任 + 自己的判断 | Skill（建议层）+ Hook（确定性层）+ 分支保护 |
| 测试 | 自验证 + 黑盒测试 | 自验证 + 多层 agentic review + evals 回归 |
| 归档 | 文档 + git 就够 | 制品链即审计线索，可合规追溯 |

为什么会有这个差异？因为治理栈的前提是多人组织。职责分离的意思是"写代码的和批准的不是同一个人"——对独狼来说只有一个人，这条规则自然失效。所以独立开发者能跳过 Code Review，大厂不能。

但有一条对谁都成立：**确认环节可以合并，但不能省略**。你可以加速确认、合并确认，但可行性、技术方案、原型、测试这四个确认点，每一个都有它存在的理由——可行性确认避免白忙活，方案确认选对方向，原型确认因为做出来再改太贵，测试确认因为要站在用户角度而不是开发者角度。你可以加速确认，不能跳过确认，人的判断力是整个流程里不可替代的部分。

为什么确认环节必须存在？一个更扎心的原因是：**Agent 极其擅长给跳过纪律找理由**——它会在你觉得差不多的时候说"这次可以简化一下"。把规格和确认写进文档，就是对这个合理化的结构性防御：spec 写好了，Agent 就没有"这次可以跳过"的借口。

## 关于 Skills 的一个反直觉观点

很多人关心：要不要装一堆开发类 Skills 来增强 Agent 的编码能力？

答案可能出乎意料：**大部分开发类 Skills 是没必要的**。大模型在编码方面已经训练得极好了，简单的自然语言提示词就够了。你不需要复杂的 prompt engineering，不需要特殊的 coding skills。

需要的是两类，恰好对应代码两侧的瓶颈：

- **左侧——辅助设计确认的**：比如 Claude Design 这类把原型设计和 UI 设计合二为一的工具，帮你快速产出高精度原型，在代码之前就确认界面和交互。
- **右侧——自动化减少体力劳动的**：比如自动部署、自动发布这类，编码完成后那些不需要判断力但耗时间的环节；还有 `/goal` 这样的命令，让 Agent 按里程碑自动推进，减少你手动拆分任务的工作。

中间那一层——编码本身，模型已经足够好。**把精力花在流程设计上，比花在 prompt 优化上回报大得多。**

## 最后

回头看整个流程：从一个想法到完整上线，写代码几乎没花时间。时间花在哪？可行性的判断、原型的反复打磨、把自己当小白用户去测试——这些恰恰是 Agent 替代不了的部分：做不做、方向对不对、好不好用，每一个都需要人来拍板。

AI 原生开发的精髓也在于此：**开发流程还是老样子，但人的角色变了。你从写代码的人，变成了管理 Agent 的人；产出不再是代码，而是一个个判断和决策。**

为什么这两侧必须是人的？因为**判断不可压缩**。资深开发者讲不清自己为什么觉得这个方案不行，不是表达问题，是十年体感本来就压不进 30 秒论证——这恰好是 Agent 替代不了的部分。AI 时代的新核心竞争力，不是写代码，而是判断"应该构建什么"的品味。

模型的编码能力只会越来越强，人的价值会越来越集中在代码两侧。越早完成这个角色转换，你从 AI 手里拿到的杠杆就越大。

这套流程跑起来，本质上还是那句老话——实践、认识、再实践。只不过现在，实践由 Agent 执行，认识由人来下。
