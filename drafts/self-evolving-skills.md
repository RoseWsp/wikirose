# Skill 会自己进化吗？一次浏览器故障、三个真实 case、一套可复制的方法

上周五，我遇到一个典型的"skill 坏了"的场景。

我的 web-access skill 访问一个登录网站突然非常费劲，agent 反复折腾进不去。我翻了整份 agent 工作日志才找到原因：新版 Chrome（v136+）启动调试模式必须显式指定 `--user-data-dir=C:\ChromeDebugProfile`，否则调试端口根本不生效。

我把这条教训写进了 skill 文件，问题解决，下次运行自动继承。

单看这只是一个 bug 修复。但放大看，它就是"让 agent 自我进化"这件事最微小的完整切片——**agent 失败 → 我读日志 → 诊断 → 改 skill → 下次自动变好**。

这篇文章想做的，就是把这个切片放大成系统：怎么让 skill 自己进化。

## 一、Agent 最大的问题：没有记忆

先说 Warp 的故事。Warp 是一个很火的 AI 终端工具，他们在内部让 agent 做代码审查，效果很差。工程师抱怨 agent 不了解项目、不知道团队规范、记不住历史经验——**就算你当面指出问题，它下次还是犯**。

Warp 做过很多补救：手动改系统提示词、完善 AGENTS.md。都没用。

然后他们悟了：**反馈给 agent 的信息，在会话结束的那一刻就消失了。** 这是 agentic loop 里丢失的最关键的上下文。

这不只是"没有记忆"，更准确地说：**人每次的纠错，都没有沉淀成下一次的能力。** 你说一百遍"我们项目里全局变量这么命名"，agent 还是不知道。

## 二、Warp 的解法：两个 skill + 人类反馈

Warp 的方案是建立在 Agent Skills（文件形式的技能包）上的自改进循环，由两个 skill 组成，中间夹着人类反馈：

- **基础 skill（inner skill）**：装着领域知识和工作指令，干活时用。比如 PR 一开，代码审查 agent 就带着它跑。
- **人类反馈**：在 PR / issue 上写评论就行——越具体越好。"你建议改这个变量名，但我们团队的规范是这种全局变量用这种命名"，这种话就是在教 agent 下次怎么做对。
- **改进 skill（improver skill）**：一个"观察者 agent"，按计划定期跑（不跟任务跑）。它拉取攒下来的人类反馈，对比"agent 当时建议了什么"vs"人是怎么回应的"，然后给基础 skill 提一个**小而聚焦的修改**。

因为 skill 就是普通文件，agent 天然很会改文件。改完走正常的 PR / code review 流程——可审查、可合并、可回滚。合并后，下一次运行自动继承改进。**最后那个"人点合并"的动作把循环关上，也保证了人永远控制着改动。**

宝玉在解读里把这一步提炼得很准：

> 不是模型自己去改进自己，而是 Agent 根据人类对模型结果的标注（人类对代码审查的评论），去改进技能。

人负责高纬度的标注、评论、反馈，agent 做执行，并根据人的反馈去改进自己的 skill。

## 三、三个真实 case：三种反馈信号，三种命运

Warp 的机制在代码审查这种领域很好用。但它普适吗？我自己攒了三个 case，恰好构成一组对照实验。

**Case 1：反编译 JS 的 skill —— 可验证，一直变好，但文件膨胀**

我写过一个反编译 JS 代码的 skill，每次 agent 遇到新场景、解决了，就自己更新 skill。效果一直不错，能持续优化。唯一的毛病：skill 文件越来越大。

**Case 2：写作的自我进化 skill —— 没有标准，负优化**

我还研究过写作的自我进化 skill，效果一言难尽。因为它其实没有统一标准——今天说"要简洁"，明天说"要有细节"，反馈互相矛盾。agent 从互相打架的信号里学习，结果就是负优化，越写越糟。

**Case 3：web-access 的 Chrome 修复 —— 环境漂移，客观，难在诊断**

就是开头那个 case。新版 Chrome 改了行为，agent 按旧知识反复失败。修复后一次到位、永久生效。

把三个 case 摆一起，一条规律浮出来了——**skill 能不能自我进化，取决于你的反馈信号属于哪种类型**：

| 信号类型 | 例子 | 收敛性 |
|---|---|---|
| 人类偏好 / 方向 | Warp 的 code review；我的写作 | 有隐含标准 → 收敛；没标准 → 发散、负优化 |
| 客观金标准 / 可验证 | 反编译、测试通过、部署成功 | 收敛，agent 可自证 |
| 环境漂移 | Chrome 升级、API 变更 | 客观，难在诊断，编码是机械的 |

写作 skill 失败，不是"自我进化这条路错了"，而是**在没有标准答案的领域让 agent 盲采反馈**。

## 四、两个隐藏的坑

**坑一：负优化。** 没有统一标准的领域，agent 从噪音里学。Warp 的处方是：有标准答案的领域（测试过没过、部署成没成功），先建一个验证 harness，让 agent 自己对着跑；没标准答案的领域（代码风格、文档质量），只采信领域专家的判断，别把反馈开放给所有人。

**坑二：文件膨胀。** 自我改进循环只会"追加"，不会"剪枝"。skill 文件像考古地层一样一层层堆——我这三个 skill 全都撞上了。所以**改进循环必须同时是压缩循环**：定期扫死分支、淘汰过时 workaround、合并冗余规则。你那条 Chrome v136 的修复，等新版本普及后就是死重。

## 五、怎么搭一个真正自动化的自进化系统

从单人到多用户平台，Warp 的架构都能搬，但要做几处改造。

**单人场景（个人 skill）：**

1. **传感器**：每个 skill 加一句统一指令——"遇到未覆盖的失败，把错误 + 日期追加到 failures.log，再求助"。反馈在失败当场被捕获，不用事后翻日志。
2. **金标准**：你手动改 skill 留下的 git diff，是最高质量的反馈信号，自动捕获。
3. **改进者**：一个 skill-improver agent 定期读 failures.log + 最近 diff，起草小编辑提案（每条必须带"为什么"）。
4. **审批门**：你只看提案，approve / reject / 改。

**多用户平台（比如我给公司内部做的 agent 平台）：**

定时任务扫描所有用户的 agent 工作记录。但这里有个关键纪律——

**耗时短不代表做得好。** agent 可以又快又错——3 轮内给你编一个看起来很专业的错误答案。光看耗时，这个象限完全看不见。所以要用三个信号通道合起来：

- **遥测**（轮次 / 工具调用数，不是墙钟时间）→ 大海捞针找出"慢而差"
- **用户信号**（重做、踩赞、一句吐槽）→ 抓"快而差"——这是耗时看不见的最危险象限
- **验证 harness** → 给可验证的领域一个客观裁判

| | 做得好 | 做得差 |
|---|---|---|
| **快** | 完美，无需动作 | **最危险**：自信地快速犯错，遥测全盲 |
| **慢** | 复杂任务，正常 | 最明确的信号——但还得知道 why |

流程：聚类同类任务 → 复现过滤（单个慢是噪音，同一 skill 反复慢才是信号）→ 分类（缺知识 / 任务难 / 意图不清）→ 改进者起草 diff 提案 → 人工决断 → 发布推送到所有客户端 → **回流指标**（改前改后的中位轮次 / 失败率对比）。

另一个纪律：**自主度不对称**。可验证的 skill，harness 自证通过后可以自动合、自动推，人只看 changelog；不可验证的，只提案、等人点头，而且只采信用户明确的负面标记。

## 六、Warp 的六条最佳实践

最后，把 Warp 的经验浓缩成六条，每条都能直接用：

1. **写原则，不写死规则**：像指导一个聪明人，不是给计算机编程。"寻找重复代码"比详尽的变量命名规则有效。
2. **解释为什么**：说明规则背后的理由，agent 才能推理、才能举一反三。
3. **让反馈零摩擦**：在人们原本工作的地方收集（PR 评论、issue），自动发生，不加额外步骤。低摩擦才有信号。
4. **保持精简，渐进式披露**：skill 文件引用资源文件和脚本，别把所有内容一次性塞进上下文。
5. **反馈质量 > 数量**：资深工程师一条详细反馈，胜过一堆点赞踩。因为赞/踩不说"为什么"。
6. **改进者的 skill 本身要写好**：它是通用的、可复用的机制，换个领域知识就能服务下一个 skill。

## 结尾

回头看那个周五：web-access 坏了，我读日志，改 skill，修好了。这套动作如果全交给一个系统来做——失败自动被捕获，改进者自动起草，我只需要在提案上点个批准——那我手里的就不再是一个个会坏的 skill，而是一支越用越准的军队。

**会自我进化的不只是 skill，是这套"人给方向、agent 执行、反馈回流"的协作方式本身。**
