## TCP 三次握手：一场关于信息论本质的深度探源

> *「所有看似约定俗成的工程决策背后，都藏着一个数学上的最优解。三次握手不是拍脑袋的产物，它是分布式系统中身份互信的信息论下界。」*

---

## 一、先忘掉课本上的话

每本教科书都会告诉你：TCP 三次握手是为了「防止历史重复连接的初始化」。然后画三个箭头，SYN、SYN+ACK、ACK，背下来考试就过了。

**但这不是理解，这是记忆。**

真正值得追问的是一个更深刻的问题——

> **在一条不可靠的信道上，两个没有先验知识的实体要达成双向通信的共识，信息交换的理论最小次数是多少？**

答案是 **三次** 。不是工程经验，不是历史包袱，是逻辑必然。

接下来，我们从零开始，把这件事掰碎了重建。

---

## 二、先定义问题：到底在「握」什么？

很多人把三次握手理解成「打招呼」，这是肤浅的。握手的本质是 **四件事** 的确认：

| 能力 | 含义 |
| --- | --- |
| A 的发送能力 | A 能把数据发出去 |
| A 的接收能力 | A 能收到对方的数据 |
| B 的发送能力 | B 能把数据发出去 |
| B 的接收能力 | B 能收到对方的数据 |

一条 TCP 连接是 **全双工** 的。也就是说，A 和 B 都必须确信： **自己能发、自己能收、对方能发、对方能收** 。四个命题，缺一个都不能开工。

现在问题变成了： **确认这四个命题，最少需要几次报文交换？**

---

## 三、两次为什么不够？——用反证法碾碎幻想

### 3.1 假设两次就够

```
第 1 次：A → B : SYN (seq=x)
第 2 次：B → A : SYN+ACK (seq=y, ack=x+1)
```

站在 **A 的视角** ，收到了第 2 次报文后：

- ✅ A 知道自己 **能发** （因为 B 显然收到了 SYN）
- ✅ A 知道自己 **能收** （因为此刻正在收 B 的报文）
- ✅ A 知道 B **能收** （B 对 seq=x 做了正确的 ACK）
- ✅ A 知道 B **能发** （B 的报文到了）

A 很满意。 **但 B 呢？**

站在 **B 的视角** ，发出了第 2 次报文后：

- ✅ B 知道自己 **能收** （收到了 A 的 SYN）
- ✅ B 知道 A **能发** （A 的 SYN 到了）
- ❌ B **不知道** 自己 **能发** （第 2 次报文发出去了，但没人告诉 B 它到达了没有）
- ❌ B **不知道** A **能收** （同上，A 有没有收到？不确定）

**B 是瞎的。B 往黑暗中喊了一嗓子，回声还没来。**

在两次握手的世界里，B 就要开始分配资源、建立连接状态了。这引出一个经典的致命问题——

### 3.2 SYN Flood 的原始形态

假设两次握手成立。A 发出一个 SYN 后就跑了（或者这个 SYN 根本是伪造的）。B 收到后立刻建立连接、分配缓冲区、记录状态。

A 永远不会来了。

**B 成了一个在雨中等一个不会来的人的傻子。**

更恶劣的情况：假设网络中存在一个 **延迟的历史 SYN 报文** （old duplicate segment）。这个报文可能是上一次已经关闭的连接的残留。B 收到后认为是新连接，分配资源，开始傻等。

这不是理论推演。这是 RFC 793 在 「The principle reason for the three-way handshake」 一节中 **明确指出** 的场景：

> *「The principle reason for the three-way handshake is to prevent old duplicate connection initiations from causing confusion.」*

**两次握手下，B 无法区分一个合法的新连接和一个幽灵般的历史报文。**

### 3.3 信息论视角的严格论证

我们换一个更硬核的角度。

定义 $C_{A}$ 为 A 选择的初始序列号（ISN）， $C_{B}$ 为 B 选择的初始序列号。一条 TCP 连接的唯一标识是 $\left(\right. I P_{A} , P o r t_{A} , I P_{B} , P o r t_{B} \left.\right)$ 加上 **双方的 ISN 共识** 。

建立连接的本质是：

$\boxed{A 知道\text{ } C_{B} \land B 知道\text{ } C_{A}}$

并且双方都知道 **对方已经知道了自己的 ISN** 。

这是一个 **同步问题** （synchronization）。让我们看看信息的流动：

第几次 方向 携带的信息 完成了什么 1 A→B $C\_A$ B 获知 $C\_A$ 2 B→A $C\_B$，以及

| 1 | A→B |  | B 获知 $C\_A$ |
| 2 | B→A | $C\_B$，以及"我已获知 $C\_A$" | A 获知 $C\_B$；A 确认 B 已知 $C\_A$ |
| 3 | A→B | "我已获知 $C\_B$" | B 确认 A 已知 $C\_B$ |

**三次之后，双方都知道了对方的 ISN，并且都确信对方知道了自己的 ISN。**

两次呢？缺了第 3 步。B 把自己的 $C\_B$ 发给了 A，但 B 不知道 A 有没有收到。B 根本不敢发数据——因为 A 可能根本不知道从哪个序列号开始算。

**两次不够，是因为信息不对称还没有消除。**

## 四、四次为什么多余？——奥卡姆剃刀的优雅裁决

### 4.1 「拆开」看看四次是什么

理论上，握手可以是四次的：

```
第 1 次：A → B : SYN (seq=x)
第 2 次：B → A : ACK (ack=x+1)
第 3 次：B → A : SYN (seq=y)
第 4 次：A → B : ACK (ack=y+1)
```

第 2 和第 3 步分别是 B 对 A 的确认和 B 自己的同步请求。但仔细看——

**第 2 步和第 3 步的方向相同，发送者相同，完全可以合并成一个报文。**

这就是 SYN+ACK。TCP 报文头里 SYN 和 ACK 是两个独立的标志位，天然支持叠加。合并不丢失任何信息，只是少发了一个报文。

$4 次 \overset{合并同方向报文}{\rightarrow} 3 次$

所以四次握手在逻辑上完全等价于三次握手，只是浪费了一个 RTT。没有任何额外的信息增益。

**奥卡姆剃刀说：如果两个方案效果相同，选简单的那个。**

### 4.2 为什么挥手是四次而握手不是？

很多人会追问：那为什么断开连接是四次挥手（FIN、ACK、FIN、ACK）？

因为 **断开是非对称的** 。

A 说「我不发了」（FIN），B 说「知道了」（ACK）。但此时 **B 可能还有数据没发完** 。B 不能立刻发 FIN，它需要把缓冲区里的数据排空。所以 B 的 ACK 和 B 的 FIN 之间存在一个 **时间差** ，无法合并。

$握手：\text{SYN }和\text{ ACK }可以合并 \Longrightarrow 3 次$

$挥手：\text{ACK }和\text{ FIN }之间有延迟 \Longrightarrow 4 次（但也可能退化为\text{ 3 }次）$

是的，如果 B 在收到 FIN 时恰好也没有数据要发了，B 的 ACK 和 FIN 也可以合并，挥手也会变成三次。这在实际抓包中经常看到。

## 五、从更高的维度审视：两将军问题的幽灵

### 5.1 你永远无法达成完美共识

密码学和分布式系统中有一个著名的 **两将军问题** （Two Generals『 Problem）：

> 两支军队在山谷两侧，需要约定同时进攻。信使穿越山谷可能被截获。无论发多少次确认，都无法达成 100% 确定的共识。

这个问题 **已被证明无解** 。

那三次握手怎么就行了？

**因为 TCP 没有要求 100% 确定。**

三次握手的设计哲学是： **把不确定性压缩到可以容忍的程度，然后用超时重传兜底。**

- 第 3 次 ACK 丢了？B 没收到 ACK，会重传 SYN+ACK。
- A 收到重复的 SYN+ACK？A 重传 ACK。
- 整个过程不通？超时，报错，上层处理。

**三次握手不是要消灭不确定性，而是要在不确定的信道上建立「足够好」的共识。三次，是「足够好」的最小代价。**

### 5.2 形式化一下

设：

- p 为单次报文成功到达的概率
- 三次握手全部成功的概率为 p^3

如果加到四次（无额外信息的纯确认），成功概率变为 p^4，反而 **更低** 了。

更多的确认轮次不会提高可靠性——这正是两将军问题的诅咒。每多一轮确认，引入的新的不确定性（「这一轮的确认到了吗？」）恰好抵消了它带来的确定性增益。

**所以不是「三次够不够」的问题，而是「超过三次没有意义」的问题。**

## 六、操作系统内核视角：资源分配的时机

抛开理论，从工程实现上看，三次握手还有一个非常现实的好处—— **延迟资源分配** 。

### 两次握手的资源困境

```
B 收到 SYN → 立刻分配 TCB（传输控制块）→ 等待……
```

如果 SYN 是伪造的，这块内存白分配了。成千上万个伪造 SYN 涌来，B 的内存就被耗尽了。这就是 **SYN Flood 攻击** 的原理。

### 三次握手的防御空间

```
B 收到 SYN → 发 SYN+ACK（可以用 SYN Cookie 不分配状态）→ 收到 ACK → 这时才分配资源
```

三次握手给了 B 一个 **验证对方存活性** 的机会：只有真正能收到 SYN+ACK 并正确回复 ACK 的 A，才值得 B 为之分配资源。

**第三次握手是 B 的「信任屏障」。** 没有它，B 就是互联网上最轻信的那个节点。

---

## 七、收束：为什么恰好是三次

让我们从多个独立维度汇总结论：

| 维度 | 为什么是三次 |
| --- | --- |
| 信息论 | 两个实体交换并确认两个独立随机数（ISN），至少需要 3 次报文 |
| 状态机 | 双方各需 SYN 和 ACK，同方向可合并，$2 \\times 2 - 1 = 3$ |
| 可靠性 | 超过 3 次的纯确认不增加可靠性（两将军问题） |
| 效率 | 3 次是满足约束的最小 RTT 开销 |
| 安全 | 第 3 次报文为被动方提供了验证主动方存活性的关卡 |
| 历史报文 | 第 3 次报文使被动方有能力识别并拒绝过期的 SYN |

这六条线索 **独立成立，共同收敛到同一个数字：3** 。

这不是巧合。这是好的工程设计与数学本质重合时，才会出现的优雅。

---

## 八、结语

> 三次握手不是一个经验参数，不是一个历史遗留，不是一个可以优化掉的冗余。  
> 它是 **不可靠信道上建立双向可靠通信的信息论下界** 。  
> 少一次，信息不足；多一次，徒增成本。  
> 三，恰好是那个刀锋上的平衡点。

这就是为什么，从 1981 年的 RFC 793 到今天，四十五年过去了，没有人改过这个数字。

**不是没人想改，是改不动。数学不让。**
