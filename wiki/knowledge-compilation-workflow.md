# 知识编译工作流

基于Andrej Karpathy的"LLM Knowledge Bases"理念，将知识库视为代码仓库管理的具体工作流设计，实现从原始素材到结构化wiki的自动化编译。

## TL;DR

三层目录结构（raw/wiki/outputs）配合LLM编译器，实现增量编译、健康检查和知识复利循环，让知识库像代码仓库一样可维护、可追溯、可进化。

## 核心隐喻：知识库即代码仓库

```
软件工程          →  知识库工程
───────────────────────────────
src/             →  raw/（原始资料）
build/           →  wiki/（知识条目）
logs/            →  outputs/（问答归档）
编译器            →  LLM
IDE              →  Obsidian
Lint / CI        →  健康检查
增量编译          →  只处理新增/变更的raw
```

## 三层目录结构

### 1. raw/ - 原始资料层（不可变）
```
raw/
├── articles/     # Web Clipper剪藏（带元数据：source_url, author, published, tags）
├── podcasts/     # Podwise导出（自动转录+AI摘要）
├── papers/       # 论文PDF
└── inbox/        # 待处理日报/临时素材
```

**元数据要求**：每个raw文件必须包含完整元数据，否则无法追溯来源。

### 2. wiki/ - 编译产物层（LLM维护）
```
wiki/
├── indexes/      # 索引文件
│   ├── All-Sources.md      # 所有源文件清单
│   └── All-Concepts.md     # 所有概念清单
├── concepts/     # 概念条目（由LLM从摘要中提取）
└── summaries/    # 逐篇摘要（每篇raw对应一份）
```

### 3. outputs/ - 运行时输出层
```
outputs/
├── qa/           # 问答沉淀（复杂提问的结果归档）
└── health/       # 健康检查报告（每周自动生成）
```

**平台内容分离**：成品内容（公众号、X平台、小红书）单独存放，不与wiki混同。

## 编译流程

### 阶段一：摄取（三个入口）

1. **Web Clipper**：网页文章一键保存，模板强制写入元数据
2. **Podwise**：播客自动转录+AI摘要，导出Markdown
3. **手动剪藏**：X推文等零散内容，通过Claude Code Skill（如`baoyu-url-to-markdown`）转为干净Markdown

**关键原则**：没有元数据的剪藏等于没剪。

### 阶段二：编译（核心步骤）

当`raw/`积累5-10篇新文档时触发编译：

#### 1. 逐篇摘要生成
- **输入**：raw文档全文
- **输出**：结构化摘要（核心结论、关键证据、疑点、术语）
- **存储**：`wiki/summaries/<slug>.md`

#### 2. 概念抽取与映射
- **新概念**：从摘要中提取，创建`wiki/concepts/<concept>.md`条目
- **老概念**：补充新证据到现有概念页
- **交叉链接**：自动建立概念间关联

#### 3. 索引更新
- **源文件索引**：更新`All-Sources.md`，添加新源文件摘要
- **概念索引**：更新`All-Concepts.md`，维护概念关系网络

**质量保证**：通过`CLAUDE.md`定义编译规范（摘要结构模板、概念字段要求、命名规则）。

### 阶段三：增量编译优化

- **触发条件**：只处理`raw/`中新增/变更的文件
- **效率**：首次编译可能需30-60分钟，后续增量编译只需几分钟
- **一致性**：保持新旧知识条目间的链接关系

## 健康检查系统

### 每周自动执行的三项检查

#### 1. 一致性检查
- **定义冲突**：同一概念在不同地方定义不一致（如"RAG"在一个地方叫"检索增强生成"，另一个地方变成"向量数据库搜索"）
- **解决方案**：自动识别冲突，提示人工审查

#### 2. 完整性检查
- **缺失字段**：哪些概念条目缺定义、缺例子、缺来源？
- **过时内容**：哪些条目需要更新或补充新证据？
- **孤证警告**：单一来源的结论需要特别标注

#### 3. 孤岛检查
- **入链不足**：哪些笔记入链少于2？（没有足够页面引用它）
- **出链不足**：哪些笔记出链少于2？（没有足够链接到其他页面）
- **修复建议**：自动推荐应建立的链接关系

### 健康报告输出
- **位置**：`outputs/health/YYYY-MM-DD.md`
- **内容**：问题列表 + 修复建议 + 整体健康度评分
- **价值**：搜到一条笔记时敢直接使用，无需担心"这玩意靠谱吗"

## 知识复利循环

### Q&A沉淀机制

每次对知识库的复杂提问，结果自动归档：

```markdown
---
question: "RAG和轻量索引的适用边界？"
asked_at: 2026-04-03
sources:
  - S-001 MotherDuck Obsidian RAG
  - C-042 RAG
---

# RAG vs 轻量索引

## TL;DR
规模在万级note以下，轻量索引够了。
语义搜索需求强或规模更大，上RAG。

## 结论
...

## 证据
（链接回原始来源）

## 不确定性
...
```

**价值**：三个月积累几十份Q&A文件，下次遇到类似问题，LLM直接读已有推导，无需重新推理。

### 自动技能生成

当任务涉及多次工具调用形成稳定解决路径时：
1. **任务完成**：Agent成功执行复杂任务
2. **路径记录**：记录所有工具调用和决策点
3. **技能生成**：将过程沉淀为结构化Markdown技能文件
4. **后续优化**：每次执行后自动修订技能文件

**效果**：连续使用一个月后，同类任务的工具调用次数从20+次压缩到8-10次。

## 工具链配置

### 核心工具
- **LLM编译器**：Claude Code（终端操作本地文件）
- **前端界面**：Obsidian（浏览wiki、看Graph View知识关联图）
- **摄取工具**：Web Clipper + Podwise + 手动剪藏工具

### 配置要点
1. **CLAUDE.md规范**：定义编译标准，确保输出一致性
2. **模板系统**：raw文件元数据模板、摘要模板、概念模板
3. **自动化脚本**：定期健康检查、增量编译触发

## 规模适应性策略

### 小规模（<100篇文章）
- **检索策略**：`INDEX.md`（每篇一句话摘要）+ `MOC.md`（主题地图）
- **优势**：简单、可靠、零额外成本
- **适用场景**：个人知识库初期、专题研究

### 中规模（100-1000篇文章）
- **增强检索**：添加全文搜索、标签系统
- **结构优化**：细分概念分类、增加关系类型
- **适用场景**：团队知识库、长期研究项目

### 大规模（>1000篇文章）
- **高级检索**：考虑RAG（向量数据库、语义搜索）
- **架构升级**：分布式索引、缓存机制
- **适用场景**：企业知识库、学术研究库

**核心原则**：先跑通流程，再优化基础设施。别在只有20篇文章时就搭建RAG架构。

## 实践建议

### 两周最小闭环
- **第一周**：搭`raw`→`wiki`最小循环，攒5-10篇raw，做首次编译
- **第二周**：让Q&A开始积累，启动第一次健康检查，按报告修复问题

### 持续优化节奏
- **每日**：新增raw文件，增量编译
- **每周**：健康检查，修复发现的问题
- **每月**：回顾知识增长，优化工作流
