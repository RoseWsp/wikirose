# RAG替代方案

在小规模知识库（几十篇文章、几万字）场景下，简单索引方案比复杂的RAG（Retrieval Augmented Generation）技术更高效实用的替代方法。

## 问题背景

### RAG的过度工程化（([[karpathy-llm-knowledge-management]])）
- **过早优化**：个人知识库未达到需要RAG的规模就引入复杂架构
- **维护成本**：向量数据库、embedding、相似度检索等组件增加系统复杂度
- **实际需求错配**：绝大多数个人知识库到不了需要RAG的规模

## 简单索引方案

### 核心组件
```
INDEX.md（全局索引）
├── 每篇文章一句话摘要
├── 按主题分组
└── LLM的查询入口

MOC.md（主题地图）
├── 按主题组织知识网络
├── 显示概念间关系
└── 帮助LLM理解知识结构
```

### 工作原理
1. **LLM读取INDEX.md**：快速了解wiki全貌和每篇文章核心内容
2. **定位相关文章**：基于摘要判断哪些文章与当前问题相关
3. **深入阅读**：只读取真正相关的几篇文章，而非全部内容
4. **综合回答**：基于读取的内容生成回答

## 实际效果验证

### 案例：GPU租赁价格分析（([[karpathy-llm-knowledge-management]])）
- **wiki规模**：35篇文章，几万字
- **查询**："GPU租赁价格还在涨吗？对AI漫剧生产成本有什么影响？"
- **处理过程**：
  1. LLM读INDEX.md，定位到GPU价格报告和漫剧行业文章
  2. 读取相关2-3篇文章
  3. 结合外部搜索验证时效性
  4. 生成跨文档分析结论
- **结论质量**：反直觉发现（GPU涨40%但漫剧成本从2000-5000→400元/分钟），深度分析

### 性能对比
| 方案 | 查询速度 | 维护成本 | 适用规模 | 准确性 |
|---|---|---|---|---|
| 简单索引 | 极快 | 极低 | 小规模（<100篇） | 高 |
| RAG | 中等 | 高 | 大规模（>1000篇） | 高 |
| 全文搜索 | 快 | 低 | 任意规模 | 中等 |

## 规模适应性原则

### 小规模（<100篇文章）
- **简单索引足够**：INDEX.md + MOC.md
- **无需向量数据库**：LLM能记住所有摘要
- **快速迭代**：先跑起来再优化

### 中规模（100-1000篇文章）
- **可考虑简单RAG**：基于标题/摘要的向量检索
- **混合方案**：索引定位大类，RAG精确定位
- **渐进升级**：从简单索引平滑过渡

### 大规模（>1000篇文章）
- **需要RAG**：向量数据库+相似度检索
- **分层架构**：索引→粗筛→RAG→精读
- **专业工具**：专用向量数据库和检索系统

## 认知转变

### 从"架构完美"到"先跑起来"
- **传统思维**：设计完美架构→实现→使用
- **实用思维**：最小可行方案→使用→按需优化
- **关键洞察**：架构完美但从不开始，不如简单方案持续运行

### LLM能力被低估
- **上下文理解**：LLM通过INDEX.md就能理解知识库全貌
- **关联推理**：能发现跨文档的概念链（如自动生成《推理成本》页面）
- **规模感知**：知道何时需要深入阅读，何时摘要足够

## 与编译型知识库的协同

### 天然契合
1. **索引自动生成**：LLM编译文章时自动更新INDEX.md摘要
2. **结构感知**：MOC.md反映wiki的实际知识结构
3. **动态维护**：新文章添加时索引自动更新

### 效率提升
- **预编译内容**：wiki文章已经是提炼后的知识，易于索引
- **网络化结构**：互链关系帮助LLM理解上下文
- **质量保证**：编译过程确保内容质量和一致性

## 实践建议

1. **从简单开始**：先实现INDEX.md，每篇文章一句话摘要
2. **测试查询**：用实际问题测试简单索引的效果
3. **按需升级**：只有遇到真正瓶颈时才考虑RAG
4. **保持轻量**：避免过度工程化，专注于核心价值
5. **利用LLM**：让LLM参与索引维护和优化
