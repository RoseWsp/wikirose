# Software 3.0

**TL;DR**：Software 3.0是以大语言模型（LLM）为可编程计算机的新编程范式，程序不再只是代码文件，而是由prompt、context window、文件、工具调用和外部环境组成的“上下文程序”，编程的本质变为“哪一段文字应该复制给你的Agent”。

## 这是什么

Software 3.0是Andrej Karpathy提出的软件进化框架中的最新阶段：

- **Software 1.0**：传统软件，人写显式代码，计算机按规则执行
- **Software 2.0**：神经网络时代，人设计数据集、目标函数和架构，通过训练得到模型权重
- **Software 3.0**：LLM时代，模型经过大规模任务训练后成为可编程计算机，通过自然语言指令和上下文窗口操作

### 核心转变
1. **从代码到上下文**：编程接口从编程语言变为上下文窗口（context window）
2. **从编译器到解释器**：LLM成为新的信息处理解释器
3. **从结构化到任意信息**：传统程序处理表格、数组等结构化数据，Software 3.0可以处理任意信息重组
4. **从精确规则到统计模式**：程序行为由统计模式而非精确规则决定

## 技术架构

### 上下文窗口作为新接口
`context window`是模型一次调用中能看到的全部信息：指令、历史对话、文件、错误日志、代码片段、图片、工具返回结果。Karpathy称之为操纵LLM解释器的“把手”。

**关键特性**：
- **可扩展性**：窗口大小持续增长，从几千token到数百万token
- **多模态**：包含文本、代码、图像、结构化数据等多种格式
- **动态性**：根据任务需要动态组装和更新
- **层级性**：包含系统指令、用户输入、工具输出等不同层级的信息

### 编程范式的变化
#### 传统编程
```python
def install_opencl():
    # 检测操作系统
    # 下载对应版本
    # 安装依赖
    # 配置环境变量
```

#### Software 3.0编程
```
"安装OpenCL，适配我的机器环境，遇到错误自己调试"
```

**本质区别**：传统编程需要预见到所有可能情况并写入代码；Software 3.0只需要描述意图，LLM根据上下文动态决定执行路径。

### 程序边界扩大
在Software 3.0中，“程序”可能包含：
- 一段自然语言说明
- 一个包含相关文件的上下文窗口
- 一组工具调用权限
- 一个测试环境
- 模型内部预训练的大量统计结构

## 关键案例

### MenuGen的两种实现
Karpathy的MenuGen应用展示了Software 2.0与3.0的深刻对比（[[karpathy-interview-agentic-engineering]]）：

#### Software 2.0实现
1. 上传菜单照片
2. OCR识别文字
3. 提取菜名
4. 调用图像生成器生成菜品图
5. 重新排版渲染
6. 部署到Vercel

#### Software 3.0实现
1. 把菜单照片交给Gemini
2. 指令：“让Nano Banana把这些菜品图叠加回菜单上”
3. 返回一张新的图片：原菜单仍在，菜品位置已渲染进图片

**关键洞察**：Software 2.0的实现是多余的，因为模型原生能力直接覆盖了任务。这不是“加速”，而是“替代”。Karpathy认为他原来写的MenuGen是多余的，因为它还停留在旧范式里：“我的整个MenuGen都是多余的。它还停留在旧范式里。那个App不应该存在。”

这个案例揭示了关键商业判断：许多AI应用不是会被做得更快，而是会被模型原生能力直接吞掉。传统代码擅长处理结构化数据（表格、数组、数据库字段、明确规则），但LLM可以处理更一般的信息重组。Karpathy强调：“更令人兴奋的不是把已有东西做得更快，而是那些以前根本不可能存在的东西。”

### 安装脚本的进化
传统安装脚本需要适配各种机器、平台和环境，随着目标环境变多，脚本会不断膨胀，最后复杂到很难维护。在Software 3.0里，安装说明本身可能就是一段可以复制给Agent的文本。Agent会读取机器环境，执行步骤，遇到错误再调试。

## 能力特性

### 超越结构化处理
传统程序擅长处理结构化数据：表格、数组、数据库字段、明确规则。Software 3.0可以处理更一般的信息重组：

- **知识编译**：把文章、文档和事实重新编译成个人或组织wiki
- **创意重组**：根据风格描述重新组织内容
- **跨领域连接**：发现不同领域信息之间的隐含关联
- **模糊推理**：在信息不完整的情况下做出合理推断

### 创造新可能性
Karpathy强调：“更令人兴奋的不是把已有东西做得更快，而是那些以前根本不可能存在的东西。”

**以前不可能的例子**：
- 实时根据上下文生成个性化UI
- 从原始视频流直接理解场景并采取行动
- 动态重组知识结构以适应不同认知需求
- 让非程序员创建复杂的数据处理流程

## 工程挑战

### 可预测性问题
传统软件的行为由代码完全确定，Software 3.0的行为有统计随机性：

- **输出不确定性**：相同输入可能产生不同输出
- **边界模糊**：很难精确定义系统的能力边界
- **错误模式新颖**：错误可能不是bug，而是统计偏差

### 测试方法论变革
传统测试方法部分失效，需要新的验证方式：

- **概率性测试**：测试通过率而非绝对正确性
- **分布测试**：检查输出是否在可接受分布范围内
- **对抗性测试**：用红队攻击发现模型盲点
- **人类反馈集成**：将人类评价纳入测试循环

### 系统集成复杂度
将Software 3.0组件与传统系统集成需要新的架构模式：

- **上下文管理**：如何在不同组件间传递和保持上下文一致性
- **状态持久化**：如何处理无状态的LLM与有状态系统的交互
- **错误恢复**：当LLM产生不可接受输出时如何优雅降级
- **性能优化**：如何减少token使用和延迟

## 未来方向

### 神经计算机愿景
Karpathy设想未来可能出现完全的“神经计算机”：
- 神经网络成为`host process`（主流程）
- 传统CPU、代码和工具调用变成协处理器
- 设备接收原始传感器输入，神经网络理解场景并生成实时UI

### Agent-first基础设施
当前工具、文档、服务和设置流程仍然主要是为人设计的。未来需要重写为Agent能读懂的输入和能安全调用的动作接口。

**理想状态**：一句“Build MenuGen”让Agent完成从写代码到部署上线的全流程，无需人工操作菜单。

### 能力民主化
Software 3.0让编程能力扩展到更广泛人群：
- **自然语言编程**：用日常语言描述需求
- **示例驱动**：通过示例而非规格定义行为
- **交互式演化**：通过对话逐步完善程序
